# The `9925257` removals are intentional; nothing was restored

**Ruling (owner, 2026-11-05, via the planning seat).** Record the removals as
intentional — *"Record as intended"*. No feature is restored from `4611f42`. The
record must not claim a restore happened, and must keep the `isAbnormalStop`
crash-resume gap open as an item awaiting its own order.

## What `9925257` was

`9925257` (2026-07-10, "recover orphaned WIP from stash@{0}") restored work that
a prior session had stashed to isolate one commit (`1812a84`, the single-file
`extensions/subagent/index.ts` commit) and never popped. The stash was
recoverable only through the dangling commits `4698a0d`, `ac791c1` and `8ca9e87`.

The consequence for this record: `9925257` is a *recovery* commit, so it both
adds and removes. Nothing in its message says which removals were decided and
which were collateral of restoring an older tree over a newer one — which is
exactly why no decision record existed. `rg -l 9925257 decisions/` returned 0
before this file.

No record existed at the time because the commit was recorded as a recovery, and
a recovery commit's message describes what it brings back, not what it drops.

"Rebuilt, not restored" is the accurate description of the first three: each
capability exists in `main` as code written after the removal, not as the
`4611f42` implementation recovered. No `4611f42` code was brought back by any
later commit, and none should be — the recoverable copy describes a 2026-04
design that the current tools have outgrown.

The strip is the one that resembles its predecessor closely enough to be worth
naming: it was removed, then rewritten as a single function covering the archive
path rather than four helpers covering the compaction path.

## Premise corrected: `isAbnormalStop` was not removed by `9925257`

The sanity check (`docs/investigations/checkpoint-sanity-check-2026-10.md` §5.8)
lists `isAbnormalStop` among the features `9925257` removed. It is not:

- `git show 4611f42:extensions/subagent/index.ts` has it at `:191-194` (doc
  comment at `:190`), used at `:542`, `:653` and `:747`.
- `git grep isAbnormalStop 9925257^` and `git grep isAbnormalStop 9925257` both
  return nothing, and the commit's diff never mentions the name.
- `git log -S'function isAbnormalStop'` names `4611f42` (added it) and
  `1812a84` (removed it) — the stash-isolation commit that `9925257`'s own
  message names as the commit the stash was made for. It names a third commit
  since 2026-11-05: `23a87f1`, this record, which quotes the string.

So `1812a84` dropped it, about **sixteen hours before** the recovery commit
(`1812a84` 2026-07-09 23:39:22 +1200; `9925257` 2026-07-10 15:29:43 +1200), not
months. The sanity check's inventory is right about the other three and wrong
about this one, and the wrong attribution is what made it read as part of the
same unexplained removal.

**`1812a84` did not delete the idea, it narrowed it.** The same commit introduced
`isFailedResult = exitCode !== 0 || stopReason === "error" || stopReason ===
"aborted"` (`extensions/subagent/_index.ts.off:188-190`), so `length`, `pending`,
`deferred` and a missing reason became "success" five days before the whole file
was disabled. Its commit message states the purpose — helpers for "the new
structured error surface" — and says nothing about dropping that coverage.

The gap opens properly at the replacement: `04dc6bf` (2026-07-14) renamed
`index.ts` → `_index.ts.off` and `b235033` (same day) created
`extensions/subagent-async/index.ts`, which has no counterpart to the predicate
at all.

## The open item

`isAbnormalStop` returned true for any stop reason other than `stop` or
`toolUse` (and for a missing one). Two call sites turned that into `isError` on
the child's result (`:542`, `:653`); the third was a TUI icon (`:747`). Nothing
in `extensions/subagent-async/` reads a child's `stopReason` (`rg -c stopReason`
→ 0; `rg -n 'agent_end|agent_settled'` → 0, against 11 `event.type ===` branches),
so a child that ends a turn abnormally while still producing text is not
distinguishable from one that finished its work.

**Scoped precisely, because the loose version of this claim is wrong:** a
*process-level* kill is visible (exit code at `index.ts:3155`, `killedMarker` at
`:3101-3109`), and the on-disk state classifier separates `Stopped`/`Killed`
from `Completed` (`extensions/lib/subagent-state.ts:243-268`). What is lost is
turn-level: the completion detector (`index.ts:2338-2344`) decides "done" from
content shape alone, so `stopReason: "length"` with text sets `isDone`, the
parent closes stdin, pi exits 0, the log footer says `Completed`, the delivered
prefix is `[Subagent X finished]` and `readSubagentState` says `complete`. Second,
independent loss on the recovery path: `:3382` keeps the footer's turn count and
discards its word and exit code, then delivers with a hardcoded exit 0 (`:3393`).

That is the crash-resume gap, and it is open, not decided. Closing it is a
separate order: the classification must be re-derived against the current
`subagent-async` result shape, which did not exist when the old predicate was
written, so restoring the function verbatim would classify nothing. Carrier:
`work-orders/WO-subagent-abnormal-stop.md`, dispatch-blocked on an owner call
between marking such a turn as abnormal and refusing to count it as done.

## Corrections (2026-11-05, re-derived against the tree)

Three claims above were wrong when this record landed, all mine:

- "`git log -S'function isAbnormalStop'` names two commits" — accurate until this

replacement written without the predicate. Both are recorded above.
