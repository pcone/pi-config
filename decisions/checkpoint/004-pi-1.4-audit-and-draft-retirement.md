# pi 1.4 upgrade audit retires the 0.83.0-era drafts; one port survives

**Ruling (recorder, WO-2026-071, 2026-11-04 — not an owner ruling).** Three of the four
remaining orders from the checkpoint sanity-check plan are retired, and the one port the audit
still finds is carried by `work-orders/WO-fleet-client-headers-env.md`. Evidence: `docs/investigations/pi-1.4-compaction-override-2026-11.md`.

| draft | disposition |
|---|---|
| `WO-pi-upgrade-1.3.0.md` | deleted. The upgrade it schedules has happened (1.4.0 installed 2026-10-31T20:17). Its `compaction-model.ts` scope splits three ways: the `sessionId` fix is unnecessary (the fleet call carries an `x-opencode-session` uuidv7 and opencode-go accepts it), the header/`env` fix moves to `work-orders/WO-fleet-client-headers-env.md`, and the ownership behaviour belongs to WO-2026-061. |
| `WO-summary-ownership-dispatch.md` | deleted, superseded. The owner ruled summary ownership on 2026-10-31 (`decisions/checkpoint/005-summary-ownership.md`, branch `summary-ownership`) and that ruling's carriers are WO-2026-061 and WO-2026-062. The draft's three-column table is not dispatchable: `reason` reports `"manual"` for both `/compact` and a checkpoint compaction, so two columns collapse into the marker split, and its premise that fleet calls fail in this environment is false on 1.4.0. |
| `WO-drift-decision-record.md` | kept, narrowed. The README signature drift and the `checkpoint_search` references are fixed in `main`; what remains is the missing decision record for `9925257` and its disposition column, which is blocked on Q4. |

**Why retire rather than revive.** A draft written against 0.83.0 encodes 0.83.0's facts. Two of
these three assert things 1.4.0 falsifies (the fleet path fails; `reason` splits manual
compactions), and one schedules an install already done. Reviving them means rewriting the
premise before the mechanism, which is a new order with a new premise, not this draft.

**The surviving port, and why it is not folded in.** `compaction-model.ts` forwards
`ProviderHeaders` (`Record<string, string | null>`) into `compact(…, headers?: Record<string,
string>)` and drops `auth.env`. No runtime symptom today — the live fleet call succeeds and the
opencode-go path produces no null headers — so it is latent, not broken. It ships as `work-orders/WO-fleet-client-headers-env.md`,
blocked on WO-2026-061 landing, because both orders edit the same handler and 061 has not merged.

landed `003` (wait-state, 2026-11-02), so it took `005` and landed on 2026-11-04 (WO-2026-073).
This record took `004`.
