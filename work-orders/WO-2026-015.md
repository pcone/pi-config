### Task Summary

**One-sentence description**: Cut review-round wall-clock time by having reviewers trust-and-audit the implementer's build/test output instead of re-running builds (R1), passing a project-context digest so reviewers stop re-reading all project docs (R2), overlapping the implementer's remaining verification with the review round (R5), and lowering thinking effort for the cheap fast agents if pi supports per-agent thinking config.

**Goal**: Shrink the dominant latency of the post-implementation review loop without weakening the safety nets (coverage matrix, targeted tests, adversarial posture, two parallel reviewers, 3-round cap, gate kinds all unchanged).

### Background (investigation findings)

1. **R1 — duplicated build/test**: the implementer runs full build+tests in its structural-verification step (`agents/implement-flash.md` ~83–103, same in `implement-pro.md`), then `review-code` re-runs the same build+test+lint (~`review-code.md` 73–80). The reviewer's build run is the dominant wall-clock item of a review round (1–5 min). `review-tests` already defers the full-suite check to review-code and runs only targeted tests — that stays.
2. **R2 — duplicated doc reading**: both reviewers are instructed to read the project's AGENTS.md/glossary/design docs/decisions from scratch (`review-code.md` ~29–31, `review-tests.md` ~29–35). The implementer has already read these; a digest with citations lets reviewers spot-check instead of re-read.
3. **R5 — serialization**: implementer prompts demand strictly ordered steps ("Follow these steps in order", `implement-flash.md` ~47–48): full structural verification BEFORE launching reviewers. Reviewers don't depend on the audit items — only on final code + build/test output — so the audit items can overlap with the review round.
4. **Thinking levels**: `settings.json` sets `defaultThinkingLevel: "high"` globally; no per-agent override exists in this repo. Generated thinking tokens are pure wall-clock. implement-flash/scout-code/scout-web do mechanical work where `low` may suffice. **Unknown**: whether pi supports per-agent thinking config — you must discover this from the pi docs (see Files to read).

### Implementation Specification

**Detailed requirements**:

**R5 — overlap verification with review (implementers)**. Rewrite the step ordering in both implementer prompts to:
1. Implement.
2. Run full build + tests (+ lint if the project has one) and capture the complete output. Build/test failure → fix and re-run BEFORE launching reviewers (reviewers must never be launched on a red build).
3. Launch both reviewers in parallel IMMEDIATELY, including in each reviewer task: (a) the work order text, (b) draft completion report, (c) files changed, (d) the full build/test/lint output with the command(s) run and the git commit/dirty-state at run time, (e) the project-context digest (R2), (f) assumptions/deviations/issues.
4. WHILE reviewers run, complete the remaining structural-verification audit items (entry-point correctness, input validation scope, test surface, recovery logic, no-unrequested-changes diff audit) and finalize the completion report.
5. When reviewers return, reconcile their findings with your audit results before deciding the verdict path.
Replace the "follow these steps in order / do not skip" language accordingly — the mandatory-order requirement now applies only to: implement → green build/test → launch reviewers.

**R1 — trust-and-audit build output (review-code, both depths)**. Replace the unconditional "run build/test/lint yourself" instruction with:
- The implementer's handoff includes the full build/test/lint output, the exact commands, and the commit/dirty-state at run time.
- Default: AUDIT the output — check it against the claimed test surface (test counts plausible, no skipped/todo tests hiding gaps, warnings examined, failure-free tail), and verify the working tree still matches the state the output was captured at (e.g. `git status`/`git diff` cheap check — files unchanged since the run).
- RE-RUN the build/tests yourself ONLY when: output missing/truncated, tree state diverged since the run, output looks inconsistent with the code you read, or anything smells. State in your report which path you took and why (one line: `build_verification: trusted-output | re-ran — <reason>`).
- Lint: same rule (audit provided output; run yourself only if absent or suspect).
- Any build/test failure you DO observe (whether in audited output or a re-run) remains automatic FAIL — unchanged.

**R2 — project-context digest (implementers produce, all four reviewer variants consume)**.
- Implementer handoff gains a "Project context digest": the conventions/invariants/error-handling patterns it relied on, each with a `file:line` citation to the source doc/code.
- Reviewer prompts: use the digest as primary orientation; spot-check at least 2 of its citations; read the full project docs (AGENTS.md/decisions/design docs) only if the digest is absent, citations don't check out, or the code contradicts the digest. Absent digest is not itself a rejection — fall back to reading the docs as today.

**Thinking levels (discovery-gated)**:
- First, determine from the pi docs whether per-agent thinking/reasoning effort is configurable (agent frontmatter key, `models.json` per-model key, or `settings.json` structure). Cite the doc file + section in your report.
- If supported: set thinking effort `low` for `implement-flash`, `scout-code`, `scout-web`. Leave everything else (including the global `defaultThinkingLevel: "high"`) untouched.
- If NOT supported: change nothing; report the finding under `issues_encountered` with the doc evidence, as a follow-up item.

**Required test boundary**: these are prompt/config changes — the boundary is textual/structural verification, not runtime tests: grep-verifiable properties (below) plus reviewer structural review. If thinking config lands in a JSON file, validate it parses and matches the documented schema (run pi's config validation if the docs describe one).
