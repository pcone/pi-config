### Task Summary

**One-sentence description**: Make the checkpoint summary the authored fields verbatim followed by a deterministic machine block, carry file-op details across checkpoints, and enforce the documented field contract with `none` as the explicit N/A token.

**Goal**: The text a fresh window receives after a checkpoint is exactly what the checkpoint call authored, plus facts only tooling knows — and a thin checkpoint call fails loudly instead of landing a thin resume context.

### Ruling input (owner 2026-10-31 → `decisions/checkpoint/003`)

- Authored fields are stored **verbatim**; the machine block is **appended**, never merged into the prose and never replaced by a paraphrase.
- Fields fail early: `[]` and omitted values are rejected; the literal `"none"` / `["none"]` is the explicit N/A token, as the schema descriptions already state.
- Checkpoint entries carry **no `usage`** (no summariser call happens).

### Premise — VERIFIED 2026-10-31 (installed pi 1.4.0)

- `session_before_compact` receives `preparation.fileOps` and `preparation.firstKeptEntryId`; the `checkpoint` tool handler does not (it compacts at `turn_end`), so file facts and the preserved-read set are available at exactly one site: `checkpoint.ts`'s `session_before_compact` handler (`:499-526`).
- `captureGitBinding(cwd)` exists (`lib/checkpoint-meta.ts:60`) and returns `{head, branch, dirty}`; it does **not** return ahead/behind.
- Core refuses to inherit file-op details from a hook-supplied compaction (`dist/core/compaction/compaction.js:19-27`: `if (!prevCompaction.fromHook && prevCompaction.details)`), and every checkpoint compaction is `fromHook`. Two of the three live checkpoints on 2026-10-31 had `details`; the third had none and nothing inherited.
- `relevantPaths` produced zero bytes across three live checkpoints. ### Implementation Specification

1. **Machine block.** Build from typed facts and append after the authored text, under a heading that cannot be confused with an authored field:
   - git: branch, short HEAD, clean/dirty, ahead/behind (extend `captureGitBinding`; non-git cwd → the block says `git: none` rather than omitting the line).
   - files read / files modified: from `preparation.fileOps`, unioned with the previous checkpoint compaction's `details` found walking `branchEntries` backwards; sorted; deduped. Rendered as comma-separated repo-relative paths.
   - archive: the path plus the `rg` hint (today only in the follow-up message, so `continue:false` loses it).
   - injection: the injected text when `relevantPaths` produced some, otherwise the omitted/changed note — never nothing. This is the same block the follow-up message used to carry.
   - tokens: before → after (after patched at `onComplete` if the entry carries it; when unknown at compose time the line says `after: unknown`, which is a fact, not a fallback).
2. **`details`.** Return `details: {readFiles, modifiedFiles}` (merged as in 1) on the `CompactionEntry` so file tracking survives without core inheritance.
3. **Injection wiring.** Always build it (it now belongs in the summary, which exists whether or not work continues); the follow-up message decides only whether the injection text is *also* sent. Remove the current `doContinue &&` dependency at `:466` in favour of consuming the composed text.
4. **Never drop a requested path silently.** Every `relevantPaths` entry ends up in exactly one bucket, rendered: injected, already-in-tail, changed-since-read, or no-tracked-region (new bucket, with the remedy: "re-read after compaction").
5. **Field validation**, at `execute()` before any archive or compaction side effect:
   - `goal`: non-blank.
   - `filesTouched`, `decisions`, `triedAndFailed`: arrays; `[]` rejected; `["none"]` accepted (explicit N/A); any whitespace-only entry rejected.
   - `constraints`: non-blank; `"none"` accepted (explicit N/A).
   - A checkpoint where `decisions` **and** `triedAndFailed` are both `none` is rejected: nothing happened, so there is nothing to resume.
   - Return **one** tool-error result listing every offending field with its rule; no archive, no compaction, no pending state on rejection. Reuse the entry point `checkOwnerState` already uses for its error result.
6. **Schema descriptions.** They already say `["none"] when none`; make the hint state that `[]` is rejected, so the model has the rule where it reads the parameters.

**Required test boundary**: the `checkpoint` tool's `execute` and the `session_before_compact` handler, driven through pi's extension/tool seams as `tests/e2e-checkpoint.test.ts` already does (real modules, mocked session manager / model / registry). Composition rows assert the **composed summary text** surfaced in the compaction result, not an internal renderer's return value.

### Invariants

**Cross-file conventions**:
- One authored-text renderer (`renderSummary`), one machine-block builder, one composition call.
- `NONE`/`isNone` remain the single N/A convention; no second "n/a" literal.

**Default values to preserve**:
- `nextSteps` defaults to `"Continue work"`; `continue` defaults to true; `contextWindow` falls back to 200k only when the model is unknown (existing behaviour, do not change).
- Injection budget stays `0.15 × contextWindow`.

**Ordering assumptions**:
- The previous-checkpoint `details` lookup walks back from `preparation.firstKeptEntryId`'s ancestry, not from the whole entry list (off-branch reads must not leak, per §5.4).

**Error handling conventions**:
- Validation failures are tool-error results, aggregated; never throws, never partial side effects.
- A missing previous `details` is `none`, not an error; a failed git probe is `git: none`.
