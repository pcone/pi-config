## Task Summary

**One-sentence description**: Make the todo extension inject the current task list into context as a message, re-primed after compaction / resume / branch (so sessions actually follow it), and add an instruction + soft guard keeping each task to 1–2 short sentences.

**Goal**: After this change, (a) the current non-done task list is injected into context as a `display:false` message and re-primed on `session_start` / `session_tree` / `session_compact` — the moments the model would otherwise lose it — so sessions stay aligned with the list; (b) the tool `description` and a non-blocking nudge on `add`/`edit` keep tasks to 1–2 short sentences with detail in the plan doc.

## Context — read this first

`extensions/todo.ts` is a global pi extension (auto-loaded; not in `settings.json`'s extensions
array — the extensions dir is auto-scanned). It registers the `todo` tool. State is stored in
tool-result `details` and reconstructed into an in-memory `todos: Todo[]` / `nextId` / `doc`
on `session_start` and `session_tree`. Those feed **UI-only** surfaces (a widget via
`ctx.ui.setWidget`, and a `/todos` command) — never the model's context. That gap is the bug:
after compaction / resume / branch the model loses the list and drifts.

The fix mirrors the **`pendingInjection` pattern already in `extensions/modes.ts`**: inject the
full content once as a `display:false` message via `before_agent_start`, set the pending flag
on `session_start` / `session_tree` / `session_compact`, and clear it after injecting. The
message then persists in the branch for every subsequent turn until the next compaction — so
the list stays in context between re-primes without re-broadcasting every turn (which would be
redundant with the recent `todo` tool results and would churn the cached system-prompt tail).

Read `extensions/modes.ts` first — specifically the `pendingInjection` state, the
`session_compact` re-prime (line ~216), and the `before_agent_start` handler that emits the
`message` (lines ~247–267). That is the exact pattern to follow. `extensions/append-system-local.ts`
is a second `before_agent_start` example and the reference for the pure-function-plus-test
convention.

Event/result types (from pi's `dist/core/extensions/types.d.ts`):
```ts
interface BeforeAgentStartEvent {
  type: "before_agent_start";
  prompt: string;
  images?: ImageContent[];
  systemPrompt: string;
  systemPromptOptions: BuildSystemPromptOptions;
}
interface BeforeAgentStartEventResult {
  message?: Pick<CustomMessage, "customType" | "content" | "display" | "details">;
  systemPrompt?: string;
}
```
This WO uses the `message` field (as modes.ts does for the mode brief), NOT `systemPrompt`.

## Implementation Specification

### 1. `renderTodoBlock(todos, doc)` — pure, exported

Signature: `export function renderTodoBlock(todos: Todo[], doc: string | undefined): string`.

Rules (mirror the `list` action's default view — non-done tasks only):
- Heading: `` `## Current tasks` `` + (`` ` (plan: ${doc})` `` when `doc` is set).
- One line per non-done task, in array order, status-marked:
  - `in_progress` → `[>]`
  - `pending` → `[ ]`
  - `deferred` → `[-]`
  - format: `` `[${mark}] #${id}: ${text}` ``
  - (Done tasks are omitted from the lines; surfaced only via the footer count.)
- Footer (only the applicable pieces, each on its own line, ≤2 lines total):
  - If any tasks are done: `` `${done} done (hidden — /todos to view all)` ``.
  - A directive line, e.g.: `Work from this list: one in_progress at a time; mark done when complete; keep each task to 1–2 short sentences with detail in the plan doc.`
- If there are zero non-done tasks (all done, or empty), return `""` (empty string).

Keep the whole block small.

### 2. Injection: `pendingTodoInjection` flag + `before_agent_start` message

Add module state: `let pendingTodoInjection = false;`

In the **existing** `session_start` and `session_tree` handlers, after `reconstructState(ctx);`
(and before/after `refreshWidget(ctx)` — order irrelevant), add:
```ts
pendingTodoInjection = todos.length > 0;
```

Add a new handler (do **not** call `reconstructState` here — see Invariants):
```ts
pi.on("session_compact", () => {
  pendingTodoInjection = todos.length > 0;
});
```

Add the consumer:
```ts
pi.on("before_agent_start", async () => {
  if (!pendingTodoInjection) return;
  pendingTodoInjection = false;
  const block = renderTodoBlock(todos, doc);
  if (!block) return;
  return {
    message: {
      customType: "todo-injection",
      content: block,
      display: false,
      details: { count: todos.length },
    },
  };
});
```
- Inject for **all** sessions including subagents (todos are session-scoped; a subagent's own
  usually-empty list injects nothing). Do **not** add a `PI_IS_SUBAGENT` guard.
- `todos` / `doc` are the module-level vars already maintained by `reconstructState` and the
  tool actions — read them directly at handler time.

### 3. Strengthen the tool `description`

Replace the current second paragraph:
```
Use setDoc first to register the path to the detailed plan doc (e.g. setDoc with text "docs/TODO.md"). Then add one-sentence summaries referencing step numbers from that doc (e.g. "Step 3: wire up the new auth middleware"). The doc path is shown in the widget so you always know where the details live.
```
with something that keeps the setDoc/step guidance **and** adds a firm brevity rule, e.g.:
```
Use setDoc first to register the path to the detailed plan doc (e.g. setDoc with text "docs/TODO.md"), then add short task summaries referencing step numbers from that doc (e.g. "Step 3: wire up the new auth middleware"). Each task is a title, not a spec: 1–2 short sentences maximum. Full reasoning, sub-steps, and context belong in the plan doc — never in the task text. If a description is growing past two lines, move the detail to the doc and shorten the task.
```
Keep the first paragraph (Actions: …) and the rest of the description intact. Keep total
description length reasonable.

### 4. Soft brevity nudge on `add` and `edit`

Define a module constant `const LONG_TASK_NUDGE = 200;` (chars). In the `add` action's success
return and the `edit` action's success return, when `params.text.length > LONG_TASK_NUDGE`,
append a one-line note to the result text, e.g.:
` Nudge: long task — keep tasks to 1–2 short sentences; move detail to the plan doc.`
- **Non-blocking**: the task is still added/edited as requested. Do not truncate or reject.
- Apply only on the success paths (not on the error/id-required/not-found paths).

Golden tests asserting exact output. Cover:

- **All done** → `""` (no non-done tasks).
- **Single pending** → heading + `[ ] #1: ...` line + directive footer (no done-count line).

## Invariants

- **Re-prime, not every-turn**: injection happens only when `pendingTodoInjection` is set
  (session_start / session_tree / session_compact) and is cleared after one emission. The
  handler never appends to the system prompt and never re-injects on every turn.
- **Do NOT reconstruct on `session_compact`**: the compacted branch may have summarized away
  tool results, so `reconstructState` would reset `todos[]` to empty. On `session_compact` only
  set the flag from the in-memory `todos[]` (which survives compaction unchanged). This is a
  subtle bug trap — call it out in the completion report.
- **Empty → inject nothing**: `renderTodoBlock` returns `""` and the handler returns without a
  `message`, so nothing is emitted on fresh/empty sessions.
- **Subagents not gated**: no `PI_IS_SUBAGENT` check. (Intentional, differs from modes.ts —
  call it out in the completion report so the reviewer doesn't "fix" it.)
- **No module-state mutation in the handler** beyond clearing `pendingTodoInjection`; `todos` /
  `doc` / `nextId` are untouched by the injection path.
- **Existing tool actions unchanged**: every action's success/error text and `details` shape stay
  the same except the two success paths that may append the brevity nudge. `list`/`clear`/`setDoc`
  /`start`/`complete`/`defer`/`remove` behavior and renderers are untouched.
- **Widget/command/renderCall/renderResult unchanged.**
- **`description` change rewrites only the guidance paragraph**: the Actions paragraph stays.

## Context

**Prior work**: none — this is the first WO on the todo extension.

**Decisions (locked, see docs/todo-injection-fix.md)**:
1. **Message + re-prime (modes.ts `pendingInjection` pattern), NOT system-prompt-every-turn.**
   Rationale: mid-session the list is already visible via recent `todo` tool results, so
   re-sending it in the system prompt every turn is redundant and churns the cached prompt tail
   when tasks change. The message pattern injects only when the model would otherwise lose the
   list (compaction/resume/branch); between those events the message persists in context and
   tool results keep it current. The reviewer should not propose switching to a per-turn
   system-prompt append.
2. Brevity via **description instruction + non-blocking nudge**, not a hard block — legitimate
   tasks may need 3 short sentences; blocking would break valid use.
